# Prompts Stream Model — Design Document

> Factorio のベルトコンベアシステムをメタファーとする。
> ユーザーは工場管理者として、機械の入出力を監視し、レシピを調整し、成果物を選別する。

---

## Factorio 対応表

| Factorio | Prompts |
|----------|---------|
| **機械** (assembler / chemical plant / refinery) | **ノード** または **パイプラインの各 step** |
| **ベルトコンベア** | **ストリーム** (step間を流れるデータの流れ) |
| **素材** (iron plate / copper plate) | **Input** (step に入力される content) |
| **レシピ** (gear recipe / processing unit recipe) | **Prompt/Params** (step の設定: systemPrompt, userPrompt, model, temperature) |
| **モジュール** (Speed module / Productivity module) | step type 固有の追加パラメータ (attachMedia, retry, timeout 等) |
| **成果物** (gear wheel / plastic bar) | **Output** (step の出力結果) |
| **機械の GUI を開く** | Tree で ノード/step をクリック |
| **機械の入力スロット** | Input Pane (何が入っているか表示、手動で差し替え可能) |
| **機械のレシピ設定画面** | Prompt/Params Pane (現在のレシピ設定を表示、編集は別画面) |
| **機械の出力スロット** | Output Pane (何が出てきたか表示) |
| **フィルターインサータ** (iron plate だけピック) | **Filter** step type (✔保存 / ✕却下 の判断) |
| **回路ネットワークの判定器** (signal を評価) | **Evaluate** step type (AI による絶対スコアリング) |
| **スプリッター** (ベルトを2方向に分岐) | **Condition** step type (条件分岐) |
| **スチールチェスト** (シンプルな一時保管) | **スチールチェスト (Steel Chest)** (標準の名前付き共有バッファ) |
| **要求チェスト** (アイテムを自動で集める) | **要求チェスト (Requester Chest)** (データ検知による自動パイプライン起動トリガー) |
| **貯蔵チェスト** (余剰品の一時保管倉庫) | **貯蔵チェスト (Storage Chest)** (不要データ・GC対象の中間生産物の退避領域) |
| **クリエイティブモードのチェスト** (素材を無限供給) | **外部ファイル / 手入力** (Input Pane のソース選択) |
| **サーキット条件で機械を制御** | **入力ソースの動的選択** (過去 checkpoint を参照) |
| **停電 → 復電** | **Checkpoint 保存** → **復帰フロー** |
| **マウスでアイテムをつまんで移動（チェストに退避）** | 中間生産物や成果物を手動でチェストに送る / チェストからロードする |

## Overview

Prompts を Factorio の工場に見立てて再設計する。

- 各 **ノード** は機械 (assembler)。content という素材を入れ、レシピ (pipeline) で加工し、成果物 (子ノード) を出力する。
- パイプライン実行中は、各 **step** が1台の機械としてベルトコンベアで接続される。前の機械の出力は次の機械の入力に自動で流れる。
- ユーザーは工場管理者として、**機械をクリックして入出力を確認**し、**レシピを調整**し、**フィルターで成果物を選別**し、**AI に品質評価**させる。
- 各機械の入出力は **チェックポイント** として逐次保存される。停電が起きても、再開時には最後のチェックポイントから復帰できる。
- プロジェクト間のデータ受け渡しは、**「チェスト」** と呼ばれるグローバルな共有バッファのみを介して間接的に行われる。
- チェストには役割の異なる複数のタイプ（**スチールチェスト**、**要求チェスト**、**貯蔵チェスト**）を設け、手動および自動でのデータ共有だけでなく、複数プロジェクト間のイベント駆動型自動連携や、クリーンなストレージ管理を実現する。

## Stream Model — Checkpoint System

### コア概念

各 step の入出力を**チェックポイント**としてプロジェクトごとの実行履歴ディレクトリに逐次ファイル保存する。
保存したチェックポイントは任意に入力ソースとして再利用可能。
これは Factorio で言うところの**「各機械の入出力をこまめに記録し、停電後も再開できるようにする」**仕組み。

### 入力側 — 任意ソース選択可能

Input Pane でこの step の入力ソースを自由に選べる。明示的に指定しない限り、他プロジェクトのデータが混ざることはない。

| Source | Factorio | 内容・スコープ |
|--------|----------|----------------|
| **前step出力** (default) | ベルトで前の機械から流れてくる | `historySteps_[currentStepIndex_ - 1].output` (同一Run内) |
| **同一プロジェクトの過去 checkpoint** | 倉庫にしまってあった過去の製品を取り出す | `projects/{current_project}/history/*/checkpoint_N/output.json` |
| **名前付きチェスト (Chest)** | **(明示指定時のみ)** 共有チェストから指定の名前の素材を取り出して投入する | ユーザーが「チェストから搬入」を選択し、任意の `chestName` を指定してロードする。**他プロジェクトへの直接アクセスは一切不可**。 |
| **外部ファイル** | 外部から鉄板を購入して投入 | ファイルダイアログで選択したテキスト/画像ファイル |
| **手入力** | マウスで入力スロットに直接アイテムを置く | Input Pane の textarea に直接入力 |

## Project Concept & Isolation (プロジェクト概念と隔離設計)

### 1. ディレクトリ構造の隔離
データ保存場所である `%APPDATA%/Ecode/Prompts/` の直下において、プロジェクト管理情報 (`session.json`) と、各プロジェクト（タブ）のデータ実体（`data/project-日付.json`）を分けて管理する。これにより、プロジェクト間でデータが混入することを物理的・論理的に防止する。
なお、`config.json`, `providers.json`, `recipes.json`, `pipeline.json` はプロジェクト別の管理から除外された**グローバル共有データ**であり、Ecodeエディタ本体の起動時に復元され、終了時に自動でシリアライズ保存（復帰）されるライフサイクルを持つ。

```
%APPDATA%/Ecode/Prompts/
├── config.json                  ← グローバル共有データ (V2対応など)
├── providers.json               ← グローバル共有データ (プロバイダ設定)
├── recipes.json                 ← グローバル共有データ (レシピ設定)
├── pipeline.json                ← グローバル共有データ (パイプライン定義テンプレート)
├── session.json                 ← セッション管理データ (タブ一覧: どのプロジェクトがロードされるか)
├── data/                        ← 各プロジェクトごとのデータ (ノードデータ本体)
│   ├── general.json             ← 初期プロジェクトデータ
│   ├── project-20260609_180000.json ← 新規プロジェクト作成時に生成される個別ファイル
│   └── ...
├── blobs/                       ← 外部メディアファイル等のバイナリデータ
│   ├── pipeline_...
│   └── ...
└── history/                     ← パイプライン実行履歴データ
    └── ...
```

### 2. 絶対に混ざらないための3層隔離保証

プロジェクト間・ノード間でのデータ混入を**絶対に防ぐ**ため、以下の3層で隔離を保証する。

#### 層1: ファイルシステム隔離（物理）
- 各プロジェクトのデータは `projects/{project_name}/` 以下に**物理的に分離**して保存される。
- プロジェクトAのコードがプロジェクトBの `data/` `blobs/` `history/` ディレクトリを**ファイルパス経由で開くことはできない**（Storage がパスを完全に制限）。
- `%APPDATA%/Ecode/Prompts/projects/` 直下のプロジェクトディレクトリ以外からのファイル読み込みは Storage がブロックする。

#### 層2: Storage 層でのアクセス制御（論理）
- `Storage::LoadTabData()`, `LoadCheckpoint()`, `SaveHistory()` 等の全ファイルI/Oメソッドは**現在アクティブなプロジェクトのパスにのみ**アクセスを許可する。
- プロジェクト切替 (`select_project`) 時のみ、Storage 内部のベースパスが切り替わる。
- `Storage::LoadFromNamedChest()` は唯一の例外で、`chests/` 以下のみにアクセス可能。このメソッドも「現在のプロジェクト以外の `projects/` 以下には絶対にアクセスしない」ことを保証する。

#### 層3: C++ ↔ JS Bridge での経路制限（通信）
- Bridge メッセージ `search`, `history_list`, `history_detail`, `evaluate_node` などは**常に現在のプロジェクト内のみ**をスコープとする。
- JS側が `{ type: "load_tab", project: "project_B", file: "..." }` のようなプロジェクトを跨ぐリクエストを送信しても、C++ 側の `HandleBridgeMessage` は**現在のプロジェクト以外へのアクセスを拒否する**。

#### 混入防止の明確なルール
| 状況 | 動作 | 保証 |
|------|------|------|
| プロジェクトAで Pipeline ▶ Run | 読み書きは全て `projects/A/` 内 | ✅ 完全隔離 |
| プロジェクトAで過去checkpointを参照 | `projects/A/history/` 内のみ検索 | ✅ 他プロジェクトは見えない |
| プロジェクトAからチェストに手動送出 | `chests/chest_xxx.json` に**コピー**される | ✅ 元のデータは移動しない |
| プロジェクトBがチェストから手動搬入 | `chests/chest_xxx.json` から**コピー**される | ✅ チェストのデータは残る |
| プロジェクトAで検索 | `projects/A/` 内のみ対象 | ✅ プロジェクトBのデータはヒットしない |
| 貯蔵チェストから救出 | `storage_chest/` → 現在のプロジェクトへコピー | ✅ 元データは残る |
| 外部ファイルを入力 | ファイルダイアログで選んだパスのみ | ✅ 但しユーザー責任 |

### 3. 名前付きチェストを介したデータ受け渡し (自動 & 手動)
プロジェクト間の直接のデータ参照は完全に禁止し、物理的・セキュリティ的な境界を堅牢に保つ。プロジェクト間でデータをやり取りするには、必ず **「チェスト (Chest)」** 共有領域を仲介してやり取りを行う。チェストの出し入れには、「パイプラインによる自動処理」と「UIによる手動処理」の両方を利用できる。

- **A. パイプラインでの自動連携 (Chestステップ)**:
  - パイプライン上に配置可能なステップ `type: "chest"` (params: `chestName`, `chestType`, `mode`) を使用する。
  - `mode: "put"` 時は、上流から流れてきた出力を指定された `chests/chest_{chestName}.json` に自動保存する。
  - `mode: "take"` 時は、指定された名前付きチェストからデータを自動で読み込み、下流のステップへ流す。
- **B. UIからの手動連携 (手動搬出/搬入)**:
  - **チェストへの手動搬出 (Put to Chest)**:
    - ユーザーは、選択中のステップの中間出力やチェックポイント (中間生産物) を表示している状態で、Output Pane もしくは Input Pane に配置された **`[📦 チェストに送る]`** ボタンをクリックできる。
    - クリック時に任意のチェスト名 (`chestName`) の入力を求めるダイアログが表示され、指定されたチェスト名で `chests/chest_{chestName}.json` にデータがコピー出力される。
  - **チェストからの手動搬入 (Take from Chest)**:
    - Input Pane のソース選択ドロップダウンから「名前付きチェストから搬入」を選択し、任意のチェスト名を入力/選択することで、現在のプロジェクトの Input 領域にデータをロードできる。
- **効果**:
  手動によるチェスト搬出を可能にすることで、**実行中の途中データ (中間生産物/チェックポイント)** であっても、ユーザーが明示的に名前をつけてチェストへコピーすれば、安全かつ簡単に別プロジェクトへ持ち出し、連携させることができます。

## Chest Types (チェストタイプと応用)

Factorioのチェストに倣い、Prompts に役割の異なるチェストを導入し、高度なプロジェクト間連携を可能にする。

### 1. スチールチェスト (Steel Chest)
* **役割**: 標準的な静的データバッファ。データをファイルとして永続化し、別のプロジェクトが手動でロードするか、パイプラインの `take` ステップで読み込むまで静的に保持する。

### 2. 要求チェスト (Requester Chest) 🌟 [イベント駆動連携]
* **役割**: **パイプラインの自動起動トリガー**として機能するチェスト。
* **動作仕様**:
  - `mode: "take"` の Chest ステップで `chestType: "requester"` を指定する。
  - バックエンドは `chests/chest_{chestName}.json` の更新監視（ファイル書き込み検知）を行う。
  - 別のプロジェクトが対象チェストへデータを書き出した瞬間、それをトリガーとして、**この要求チェストを始端とするパイプラインをバックグラウンドで自動的に起動 (Run) し、データを流し込む**。
* **応用**: プロジェクトA（原稿執筆）が原稿をチェストに入れると、プロジェクトB（校正・翻訳）が自動で起動して処理を始めるといった、イベント駆動型の連携が可能になる。

### 3. 貯蔵チェスト (Storage Chest) 🧹 [クリーンなストレージ管理]
* **役割**: 不要な中間データや、古いチェックポイントを安全に保管する「ゴミ箱・退避用チェスト」。
* **動作仕様**:
  - 各プロジェクト内で、ユーザーによって「却下 (✕)」された出力や、実行数制限（直近50回）によりクリーンアップされる過去の `checkpoint_N/` ディレクトリは、即座に完全削除されるのではなく、グローバルな `storage_chest/` ディレクトリに自動退避（Move）される。
  - ユーザーは「あの時ボツにしたけどやっぱり使いたい」中間コードなどを、この貯蔵チェスト内から検索して手動で救出（プロジェクトにインポート）できる。
  - ディスク容量を確保したい時は、ツールバーから「貯蔵チェストを空にする」を実行するだけで一括物理削除される。

#### `chest` — チェスト（名前付きチェストを介した保管・搬出・搬入）

## Design Decisions (確定事項)

### 1. checkpoint 保持ポリシー (Garbage Collection) [Configurable]
ディスク容量を節約するため、各プロジェクトの実行履歴（`checkpoint_N/`）の保持数は Config 画面の General タブでユーザーが設定可能とする。
デフォルト: 50 runs、最小: 10、最大: 500。
超過分は貯蔵チェストに自動退避される。

### 2. バイナリ・メディアファイル (Blob) 管理
画像や音声などのバイナリ出力ファイル（Blob）は、各プロジェクト内の `blobs/` ディレクトリに分離して保存する。

### 3. 自動チェストステップ & 手動チェスト操作による隔離共有
- プロジェクト同士が、お互いのプライベートデータ（タブ、履歴、中間チェックポイント）を直接参照することは一切禁止する。
- プロジェクト間でデータを移動させるには、必ずグローバルな共有バッファである `chests/` に格納される **名前付きチェスト** を介してやり取りを行う。
  - **自動**: `chest` ステップ (`mode: "put"` / `"take"`) により、パイプライン経由で自動で搬出・搬入する。
  - **手動**: 任意の出力や **中間生産物 (チェックポイント)** を、UIの `[📦 チェストに送る]` ボタンから名前をつけてチェストへ搬出し、別プロジェクトの入力から手動でロード可能とする。

### 4. 要求チェストによるリアクティブ自動起動
- `chestType: "requester"` を指定した搬入側パイプラインは、バックエンドのチェストファイル監視機構により、データ書き込みを検知した瞬間にバックグラウンドで自動的に実行が開始される。
