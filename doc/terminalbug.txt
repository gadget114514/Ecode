Terminal: antigravity 実行時のカーソル/入力欄ドリフトバグ調査メモ
======================================================

■ 症状
- Ecode 内蔵ターミナルで `antigravity`(対話型エージェント TUI)を使用中、
  ストリーミング出力の再描画が起きている最中に文字を入力すると、
  入力ボックスとカーソルが意味不明な絶対位置へ移動する。
- ブロック内部の相対位置関係は正しい → フレーム全体が上下にドリフトしている
  ように見える。
- 他の対話型 CLI(claude 等)では再現しない → antigravity 固有の描画パターン
  (スクロール領域の使い方 / 再描画タイミング / 絵文字混じりの出力など)が引き金の
  可能性が高い。
- VT ストリームのキャプチャ(デバッグログ)は過去に何度か試して有効な再現ログを
  取れていない。今回はこのアプローチを取らず、ソースコードの静的調査を優先した。

■ 静的調査で見つかった候補(優先度順)

1. [最有力] CSI A/B (CUU/CUD) がスクロール領域マージンを無視する
   - Application/Terminal/src/TerminalBuffer.cpp: moveCursorRelative()
     (279-284行目)
   - clampCursor() (1030-1037行目) は originMode_ が有効なときだけ行を
     [scrollTop_, scrollBottom_] にクランプしている。
   - VT/xterm 仕様では CUU/CUD は DECOM の状態に関わらず、カーソルが
     スクロール領域内から移動を開始した場合はマージンで止まるべき。
   - moveCursorNextLine/moveCursorPreviousLine (CNL/CPL, 303-323行目) は
     このロジックを正しく実装済みで参考にできる。
   - antigravity が DECSTBM で入力欄を画面下部に固定し、再描画のために
     CSI A で上に戻る実装だった場合、領域外へ抜けて誤った絶対行に
     描画してしまい、症状と一致する。
   - ただし実際に antigravity が DECSTBM を使っているかは未確認
     (「■ 未確認・保留」参照)。

2. 文字幅テーブルが Node 系ツールの string-width と食い違う
   - TerminalBuffer::characterWidth() (650-696行目)
   - U+2705 ✅ / U+274C ❌ / U+26A1 ⚡ / U+2B50 ⭐ / U+2757 ❗ などの
     Emoji_Presentation 記号が幅1扱いになっている(Node 側は幅2として
     折り返し計算をする実装が多い)。
   - サロゲート範囲(0xD800-0xDFFF)を一律幅2にする雑なルールになっており、
     逆に幅1であるべき補助面文字(数学英字など)まで幅2扱いになる。
   - ストリーミング出力に絵文字が混ざると、antigravity 側とターミナル側で
     折り返し桁数の認識がずれ、再描画のたびにフレームがドリフトし得る。

3. feed() 呼び出しの境界でサロゲートペアが分断される
   - Application/Terminal/src/TerminalEmulator.cpp: 242-252行目
   - PTY からの読み取りチャンクが上位サロゲートで終わると、そこだけ単独の
     1コード単位クラスタとして処理され、次チャンクの下位サロゲートは
     別クラスタになる(幅計算・結合処理が乱れる)。
   - 過去に同種の問題を修正した実績あり(コミット 9db19fa: OSC 終端が
     チャンク境界で分断される問題)。

■ 問題なしと判断した箇所(調査済み・除外)
- DECSC/DECRC (ESC 7/8): コミット 4e54ea2 でフル属性保存に対応済み。
  pendingWrap_ も正しく保存/復元される。
- alternate screen 切り替え: メイン/オルタナ別々の保存カーソルスロットを
  持っており、切り替え時の位置ずれは確認できず。
- DSR (CSI 6n): ビューポート基準・DECOM 補正あり、WriteFront で
  優先送信されるためキー入力より先にシェルへ届く経路も確認済み。

■ 未確認・保留(今回は追わなかった)
- antigravity 本体(C:\Users\<user>\AppData\Local\Programs\Antigravity)の
  `antigravity.cmd` は Antigravity.exe + resources/app/out/cli.js を
  起動する構成だが、cli.js 内には ink 系 TUI やカーソル制御の痕跡が
  見当たらなかった(IDE 起動 / tunnel 用途の CLI と推測される)。
  ユーザーが実行している「対話型エージェント TUI」の実体コードが
  未特定のため、実際に送出される VT シーケンス(DECSTBM 使用有無、
  絵文字の使用状況など)は未確認。
- そのため上記候補1〜3はいずれも「コード上に存在する欠陥」であって
  「今回の症状の確定原因」ではない。実機での再現ログなしに確定は困難。

■ 次のアクション案(VT デバッグログ以外)
- antigravity 側のソース(npm パッケージであれば node_modules 内、
  ink/blessed 等の TUI ライブラリ利用有無)を特定できれば、それを読むことで
  実際に送出される制御シーケンスを静的に確認できる可能性がある。
- 上記候補1(スクロール領域マージン)は他の多くの TUI にも影響し得る
  一般的な仕様不備なので、再現条件が特定できなくても先行して修正する
  価値がある。
- 候補2(絵文字幅)も同様に独立して直す価値がある。
